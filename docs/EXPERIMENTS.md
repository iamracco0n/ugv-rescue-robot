# 실험 기록 — 2대 병렬 수색과 검출 실패 원인 규명

단일 로봇 수색에 **두 번째 로봇**을 붙이고, 그 과정에서 드러난 **조난자
검출 실패의 진짜 원인**을 찾아 고친 기록이다.

무엇을 왜 시험했고 어떻게 판단했는지를 남긴다. **채택하지 않은 시도까지
결과와 함께 적어 둔다** — 같은 길을 두 번 가지 않기 위해서다.

관련 문서: 요약과 최종 수치는 [README](../README.md), 로봇 대수 확장은
[SCALING.md](SCALING.md).

커밋 54개. 크게 세 갈래다.

1. 2대 병렬 수색 (구역 분할 · 지도 병합 · 동료 돕기)
2. 검출 실패 원인 규명과 수정 (카메라 기하)
3. 측정 도구와 실험 설계

## 1. 2대 병렬 수색

### 1.1 넣은 것

**표 1. 2대 구성에 넣은 것**

| 항목 | 파일 |
|---|---|
| 로봇별 이름공간(TF·토픽·노드) | `ugv.urdf.xacro`, `sim_robot.launch.py` |

| 다중 로봇 RViz | `ugv_multi.rviz`, `tf_relay_node.py` |

### 1.2 잰 것

**1200초 시점 발견 인원**으로 1대와 2대를 짝지어 비교했다. 같은 머신·같은
시간대에 이어서 돌려 머신 성능차가 안 섞이게 했다.

**표 2. 1200초 시점 발견 인원 — 같은 머신에서 짝지어 비교**

| 머신 | 2대 | 1대 |
|---|---|---|
| OMEN r1 | 7명 | 3명 |
| OMEN r2 | 6명 | 5명 |
| OMEN r3 | 6명 | 4명 |
| 메인 | 7명 | 6명 |

**4쌍 전부 2대 승, 평균 +2.0명(4.5 → 6.5).** 약 1.4배다. 두 머신에서
재현됐다.

작은 월드에서는 이득이 없었다. 2대가 값어치를 하려면 방이 충분히 많아야
한다.

> 이 수치는 조난자 자세를 바꾸기 전 월드에서 잰 것이다. 지금 월드는 누운
> 사람이 늘어 더 어렵다.

### 1.3 지표를 두 번 바꿨다

처음에는 '전원 발견까지 걸린 시간' 으로 쟀는데 못 쓸 지표였다. 7명 중 가장
늦게 찾은 한 명이 값을 정하는 최댓값 통계라 편차가 크고(같은 조건에서
700초와 2672초), 시간 안에 못 끝낸 런은 숫자가 아예 안 나와 표본에서
빠진다. 완주한 런만 비교하게 되어 편향이 생긴다.

고정 시간에 센 인원수는 둘 다 피한다. 모든 런이 값을 내고, 최댓값이 아니라
누적량이라 편차가 작다. (`tools/victims_at.py`)

## 2. 검출 실패 원인 규명

### 2.1 무엇이 문제였나

2대를 붙이고 나서도 **7/7 완주가 절반**에 그쳤다. 조난자별로 갈라 보니
원인이 하나로 좁혀졌다.

**표 3. 조난자별 발견률 (46런)**

| 조난자 | 자세 | 발견률(46런) |
|---|---|---|
| 침대 환자 | 침대에 누움 | **41%** |
| 바닥 누움 | 누움 | **70%** |
| 나머지 다섯 | 서있음·앉음 | 89~100% |

의도적으로 잔해에 가려 놓은 조난자는 **100%** 였다. 어려운 배치는 잘 찾고
**누운 자세**를 못 찾았다.

### 2.2 파라미터를 다섯 개 돌렸는데 하나도 안 움직였다

`dirs`(관측 방향 기록), `ghost`(유령 자리 기억), `room_bonus`(방 우선),
누운 사람 관문 완화, `det_conf`(박스 신뢰도). 전부 재고 되돌렸다. 근거는
각 커밋에 남겼다.

특히 관문 완화가 왜 안 통했는지가 실마리였다. 검출은 두 단계인데,

```
1단계  YOLO 가 사람 박스를 만든다     <- det_conf
2단계  박스의 관절점을 검사한다        <- 관문
```

누운 조난자를 놓친 런에서 **'후보로 잡았는데 관문에서 떨어짐' 이 0건**이고
거의 전부 **'후보로 잡은 적도 없음'** 이었다. 2단계에 도달한 적이 없으니
2단계를 아무리 풀어도 아무 일이 안 일어난다.

### 2.3 사진을 봤더니 바로 나왔다

숫자를 그만 돌리고 로봇을 누운 조난자 2m 앞에 세워 카메라 화면을 저장했다.

**몸이 화면 아래로 잘려 있었다.** 신발과 다리만 들어오고 몸통·머리는
프레임 밖이었다. 검출 박스는 안 그려졌다.

계산과 맞는다. 카메라 높이 0.5m, 수직 FOV 48.9도 — 수평으로 조준하면
**화면 아래끝이 바닥과 만나는 지점이 1.10m** 다. 그보다 가까운 바닥은
아예 안 찍힌다. 실측 검출 성공 거리도 누움 2.3~4.9m(2.3m 보다 가까운
성공 0건) 대 서있음 3.5~5.5m 였다.

### 2.4 고친 것 — 탐색 중 포탑을 아래로

`search_pitch` 기본값 0 → 0.10rad(5.7도). 화면 아래끝이 1.10m → 0.86m 로
당겨진다.

먼저 0.20 을 수평과 비교해 채택했다(2머신 18런).

**표 4. 포탑 0.20 rad 대 수평 (2머신 18런)**

| | 0.20 | 0 (수평) |
|---|---|---|
| 누운 3명 발견률 | 21/27 (78%) | 14/27 (52%) |
| 7/7 완주 | 6/9 (67%) | 2/9 (22%) |
| 누움 최소 검출거리 | 1.3m | 2.0m |

그런데 0.20 이 최적인지는 안 재봤다 — 처음 고른 값이 그냥 통한 것이다.
0.10 / 0.20 / 0.30 을 훑으니(18런, 값당 6런) **0.10 이 더 나았다.**

**표 5. `search_pitch` 스윕 (18런, 값당 6런)**

| 각도 | 누움 | 서있음 | 7/7 |
|---|---|---|---|
| **0.10** | **18/18** | **18/18** | **6/6** |
| 0.20 | 16/18 | 16/18 | 4/6 |
| 0.30 | 15/18 | 17/18 | 4/6 |

0.30 은 위쪽 시야가 7.3도까지 줄어 오히려 나빠진다. 0.10 이면 18.7도를
남기면서 가까운 바닥을 확보한다 — 대가가 가장 작은 지점이다.

### 2.5 되돌렸던 것을 다시 켰다 — `seen_min_dirs`

관측 방향 기록을 처음엔 '효과 없음' 으로 껐다. **그때는 검출이 병목이었다.**
포탑이 수평이라 누운 조난자를 52% 밖에 못 찾았고, 탐사를 아무리 잘해도 그
벽에 막혀 차이가 안 났다.

포탑을 고친 뒤 다시 쟀다(메인 15런). 지표는 '7/7 까지 걸린 시간' 이다 —
발견 인원은 이미 만점이라 구분력이 없다.

**표 6. `seen_min_dirs` 재측정 (메인 15런)**

| 조건 | 7/7 | 걸린 시간(초) |
|---|---|---|
| base | 2/4 | 1780, 954 |
| **dirs** | **4/4** | **874, 1046, 762, 1105** |
| room | 2/3 | 1267, 1036 |
| both | 3/4 | 1115, 829, 1098 |

`room_bonus` 를 같이 켠 both 가 dirs 단독보다 낮다. 방 우선 보너스는
보태는 것이 없어 끈 채로 둔다.

**한 번 재고 되돌린 것이 영영 틀린 것은 아니다.** 병목이 바뀌면 값도
바뀐다. 그래서 되돌릴 때 기능과 스위치를 남겨 두는 것이 중요했다.

### 2.6 최종 검증 — 2머신 유효 50런, 제한 1800초

두 값을 따로 쟀으므로(포탑=에일리언웨어, dirs=메인) 조합으로 다시 확인했다.
겸사겸사 머신 교차 확인도 된다. 머신당 유효 25런씩 채웠고, 같은 검증을
두 번 돌렸다(각 유효 50런). **두 번을 따로 적는다.**

**표 7. 최종 검증 — 유효 50런 2회**

| | 1차 | 2차 |
|---|---|---|
| 유효 런 | 50 | 50 |
| **7/7 완주율** | **41 (82%)** | **45 (90%)** |
| 95% 신뢰구간 | 69~90% | 79~96% |
| 완주 시간 중앙값 | 17.5분 | 19.1분 |
| lying_s2 발견률 | 42 (84%) | 47 (94%) |
| 유령 검출 | 2건 | 1건 |

**두 값은 서로 모순되지 않는다** — 신뢰구간이 크게 겹친다. 정직하게 말할 수
있는 것은 여기까지고, 대표값은 보수적으로 **82~90%** 로 읽는 것이 맞다.

#### 2.6.1 왜 합쳐서 86 %(n=100)로 적지 않았나

합치려면 두 검증이 교환 가능해야 하는데, 코드가 완전히 같지 않다.

**표 8. 두 검증의 코드 차이**

| | 1차 | 2차 |
|---|---|---|
| 궤적 로깅(1Hz) | 없음 | 있음 |
| 기각위치 로깅 | 없음 | 있음 |
| `room_far_coef` · `room_commit_area` | 없음 | 있음(둘 다 기본 꺼짐) |

목표 선택 로직은 같다. 하지만 **로깅은 공짜가 아니다** — CPU 가 병목인 2대
시뮬에서 초당 로그가 늘면 영향이 없다고 단정할 수 없다. 합산은 '로깅이
결과에 무영향' 이라는 가정 위에서만 성립하고, 그 가정은 검증하지 않았다.
가정을 받아들이면 합산은 86%(78~91%, n=100)다. 참고값으로만 남긴다.

#### 2.6.2 실험 중에 소스를 고쳤다

2차의 마지막 5런은 `room_commit` 소스를 고치는 중에 시작됐다.
`colcon build --symlink-install` 이라 `build/` 가 소스로 향하는 심링크여서,
재빌드 없이도 다음 런부터 반영된다 — **'빌드 전까지는 안전' 이 아니다.**
기본값이 꺼짐이라 해당 경로는 잠들어 있었고 그 5런에서 노드 사망도 없었지만
(탐사 목표 52~59회로 정상 범위), 실험이 도는 동안 소스를 건드리면 안 된다.

50런짜리 검증을 두 번 해서야 82% 와 90% 라는 폭이 보였다. 한 번만 재고
어느 쪽이든 확정값으로 적었으면 과신이었다.

**누운 사람과 서있는 사람의 격차가 사라졌다.** 시작할 때는 52% 대 100%
였다.

**표 9. 개선 경과**

| 설정 | 7/7 완주율 |
|---|---|
| 포탑 수평 · dirs 끔 | 22% |
| 포탑 0.20 | 67% |
| **포탑 0.10 + dirs** | **82~90%** (유효 50런 x 2회) |

무효 런은 뺐다. 2대 런에서 로봇 한 대만 카메라가 죽으면 그 런은 못 쓰는데,
실측으로 15% 가 그랬다. 그래서 'N 런 돌리기' 가 아니라 '유효 N 런이 찰
때까지' 돌리는 방식으로 채웠다 — 보충한 런에서도 또 무효가 나므로 한 번
세어 그만큼 더 도는 방식으로는 목표에 못 닿는다.

주의: 완주율은 제한 시간에 따라 달라진다. 1793초짜리 런이 있었는데 제한이
1800초라 7초 차이로 완주로 잡혔다. 시간을 더 주면 올라가고 짧게 주면
떨어진다.

## 3. 남은 한 명 — `lying_s2`

완주하지 못한 14런은 대부분 같은 사람을 놓쳤다. 남서 방 바닥에 누운
`lying_s2` 다(1차 84% · 2차 94%, 나머지 여섯은 96~100%). 매번 다른 사람을 놓치면 시간이
모자란 것이고, 매번 같은 사람이면 그 자리에 구멍이 있는 것이다.

원인을 가르려고 계측을 붙였다. 기존 로그로는 못 갈랐기 때문이다 — '탐사
목표' 는 가려던 곳이지 간 곳이 아니고, 오탐 게이트 기각은 15초마다 개수만
찍혀 어느 자리에서 죽었는지 알 수 없었다.

1Hz 궤적을 붙이고 34런을 전수로 보니 이렇게 갈렸다.

**표 10. 조난자 5 m 안까지 갔는지와 발견 여부 (34런)**

| | 발견 |
|---|---|
| 그 자리 5m 안까지 간 런 | 29런 중 **27런 (93%)** |
| 그보다 멀리서 끝난 런 | 5런 중 **0런** |

**가기만 하면 찾는다.** 못 찾은 런은 거기 안 간 것이다.

'거기' 가 어디인지도 좁혔다. 방2 는 남쪽 다섯 방 중 **유일하게 내부
칸막이가 있는 방**이고(`inner_s2`), 그 칸막이 때문에 문이 서쪽 칸의 구석에
붙어 있다. 로봇은 구석에서 들어와 15m 깊이의 주머니를 훑어야 한다. 같은
깊이(11~13m)인 다른 방들은 칸막이가 없어 문이 방 한가운데에 있다.

**표 11. 남쪽 방 구조와 발견률**

| 조난자 | 방 | 문에서 x차 | 깊이 | 칸막이 | 발견률 |
|---|---|---|---|---|---|
| lying_s4 | 방4 | -1.8 | 11m | 없음 | 100% |
| lying_n3 | 방3 | -1.0 | 12.5m | 없음 | 100% |
| occluded_s1 | 방1 | -1.9 | 13m | 없음 | 96~100% |
| **lying_s2** | **방2** | **-3.2** | **13m** | **있음** | **84~94%** |

주머니 침투 깊이로 다시 가르면 더 깨끗하다(`tools/pocket.py`).

**표 12. 주머니 침투 깊이와 발견 여부**

| | 발견 |
|---|---|
| 주머니 y<-11 까지 내려간 런 | 34런 중 **33런 (97%)** |
| 거기까지 못 내려간 런 | 6런 중 **0런** |

발견 순서도 봤다(`tools/find_order.py`). lying_s2 는 꼴찌가 아니라 중앙값
5번째, 659초에 찾힌다 — 뒤에 찾히는 occluded_s1(827초)·lying_s4(813초)의
발견률이 오히려 높다. **시간이 모자라서가 아니다.** 그리고 43런 전부 ugv1
이 찾았다(구역 분할상 방2 는 ugv1 몫이다).

### 3.1 결론 — 알고리즘 결함이 아니라 시간 예산이었다

제한 시간을 45분으로 늘려 다시 쟀다(조건당 유효 10~11런). 그러자 **기본
설정이 lying_s2 를 11런 전부 찾았다.** 30분에서 82% 였던 것이 100% 가 됐고,
주머니 침투 깊이 중앙값도 -17.1 로 커밋 방식(-16.2)보다 깊었다.

로봇은 그 구석에 갈 줄 안다. 30분 안에 못 갈 뿐이다.

같은 100런 데이터를 제한 시간별로 다시 채점하면 이렇게 된다.

**표 13. 제한 시간별 7/7 완주율**

| 제한 | 7/7 완주율 |
|---|---|
| 15분 | 10% |
| 20분 | 56% |
| 25분 | 77% |
| **30분** | **86%** |
| 35분 | 91% |
| 40분 이상 | 91% |

(30분까지는 유효 100런, 그 뒤는 45분 라운드 유효 11런 기준)

**86% 는 알고리즘의 한계가 아니라 30분이라는 예산의 값이다.** 한 숫자로만
적으면 마치 고쳐야 할 결함처럼 읽히므로 곡선으로 남긴다. 더 올리려면
탐사 정책이 아니라 시간이나 로봇 대수를 늘려야 한다.

### 3.2 시도한 여덟 가지 — 하나도 채택하지 않았다

**표 14. 시도한 여덟 가지 — 하나도 채택하지 않았다**

| 시도 | 규모 | 결과 |
|---|---|---|
| `cam_see_range` 4.5 → 3.5 | 12런 | 이득 없음 |
| `cam_see_range` 4.5 → 3.0 | 12런 | 이득 없음, 깊이 편차만 커짐 |
| `seen_min_dirs` 2 → 3 | 10런 | **해로움** (완주 2/5) |
| 누움 관문 완화 (4 / 0.35) | 20런 | 확정 실패 — 아래 참조 |
| `room_bonus` 0 → 1.5 | 12런 | 값이 너무 작아 아무 일도 안 남 |
| `room_bonus` 0 → 50 | 12런 | 이탈은 줄었으나 깊이·완주 그대로 |
| `room_far_coef` 0 → 5 | 41런 | 아래 참조 |
| `room_commit_area` 0 → 20 / 10 | **43런** | 아래 참조 |

`room_bonus` 를 두 번 적은 것은 처음이 시험이라 부르기 어려워서다. 점수는
m^2 단위이고 후보 덩어리가 84~306m^2 인데 1.5 를 얹었으니, 결정을 바꿀 수
있는 크기가 아니었다. 50 으로 다시 재니 방 이탈 횟수가 확실히 줄었다
(27~35 대 36~44, 12런에서 겹침 없음). 그런데 주머니 깊이도 완주율도 안
움직였다. **작동하지만 엉뚱한 것을 움직인다** — 이탈 횟수는 성공 런과 실패
런을 안 가른다. 성공 런도 런당 40회씩 방을 뜬다.

`room_far_coef`(같은 방 안에서 먼 후보 먼저)는 깊이를 직접 겨냥해 새로
넣은 것이다. 조건당 유효 20런으로 쟀다.

**표 15. `room_far_coef` 5.0 대 기본 (조건당 유효 20런)**

| | `far_coef 5.0` | 기본 |
|---|---|---|
| 유효 런 | 21 | 20 |
| 7/7 완주 | 13 (62%) | 13 (65%) |
| lying_s2 발견 | 18 (86%) | 14 (70%) |
| 주머니 깊이 중앙값 | -14.7 / -15.7 | -15.9 / -15.5 |

lying_s2 는 86% 대 70% 로 앞서지만 p≈0.12 라 확정할 수 없고, 완주율은
차이가 없다. **채택하지 않고 기본값 0(꺼짐)으로 둔다.** 기능과 스위치는
남긴다 — 제한 시간을 늘리는 등 조건이 바뀌면 다시 볼 값이다.

`room_commit_area`(방에 미관측이 남아 있으면 그 방 밖 후보를 아예 뺀다)는
보너스가 아니라 커밋이라 처음으로 두 지표를 동시에 움직였다. 방 이탈이
4분의 1로 줄고 침투 깊이도 깊어졌다. 그런데 결과는 라운드마다 뒤집혔다.

**표 16. `room_commit_area` — 라운드마다 뒤집혔다**

| 라운드 | 커밋 | 기본 |
|---|---|---|
| 30분 (유효 11런씩) | 5/11 (45%) | 8/11 (73%) |
| 45분 → 30분 재채점 | 9/10 (90%) | 8/11 (73%) |

기본 조건은 두 라운드에서 73% 로 정확히 같은데 커밋만 45% → 90% 로 튄다.
**두 라운드가 반대 방향을 가리키면 그건 효과가 아니라 잡음이다.** 채택하지
않고 기본값 0(꺼짐)으로 둔다.

30분 라운드에서 커밋이 놓친 조난자를 확인한 것이 결정적 단서였다. 궤적으로
가르니 '가고도 못 알아봄' 이 0건이고 전부 '거기까지 못 감' 이었다 — 놓친
사람은 죄다 건물 반대편 끝(occluded_s1, lying_s4, lying_n3)이었다. 한 방을
완벽히 훑는 대신 다른 방에 갈 시간을 잃은 것이다. 30분 안에서 꼼꼼함과
넓이를 맞바꾸고 있었고, 그래서 시간을 늘려 봤다.

임계값으로 세기를 조절하려는 시도도 실패했다. 20 과 10 이 방 이탈 횟수·
깊이·완주 시간까지 사실상 같았다. 방에 남는 미관측이 대개 100~300m^2 라
임계가 10 이든 20 이든 똑같이 '붙들어라' 로 판정된다 — 이 값은 세기 조절이
아니라 켜짐/꺼짐 스위치다.

중간에 속을 뻔했다. 21런 시점에는 완주율이 44% 대 83% 라 '해롭다' 로
보였는데, 41런까지 채우니 62% 대 65% 로 붙었다. 작은 표본의 큰 차이는
대개 노이즈다.

주의: 이 라운드의 대조군 완주율(65%)이 최종 검증의 82% 보다 낮다. 표본
차이(20런 대 50런)로 설명되는 범위이지만, 그 사이에 궤적·기각위치 계측을
추가했으므로 계측 부하의 영향도 완전히 배제하지는 못했다.

관문 완화는 처음에 4/4 대 1/4 로 크게 이겨 보였다. 그런데 조건과 머신이
붙어 있었다(완화=메인, 대조=에일리언웨어). 뒤집어 다시 돌리니 결과도 뒤집혔다.

**표 17. 관문 완화 — 조건과 머신을 스왑한 결과**

| 라운드 | 완화 | 대조 |
|---|---|---|
| 1차 | 메인 4/4 | 에일리언웨어 1/4 |
| 스왑 | 에일리언웨어 3/4 | 메인 3/3 |
| 합계 | 7/8 | 4/7 (p=0.23) |

**처음 본 큰 차이는 그 머신 그날의 운이었다.** 이후로는 한 머신 안에서 두
조건을 번갈아 돌린다(`tools/`... `alt_run.sh` 방식). 5~6런짜리 선별은
노이즈가 지배해서, 이 규모로는 이득이 확인되지 않으면 '없다' 가 아니라
'이 표본으로는 못 잰다' 로 읽어야 한다.

한계도 적어 둔다: 로봇은 **검출하면 접근**하므로 '안 감' 과 '원거리 검출
실패' 가 완전히 분리되지 않는다. 위 표의 '안 감' 에는 멀리서 못 알아봐서
갈 이유가 안 생긴 런이 섞여 있다.

### 3.4 같이 찾은 커버리지 버그

`_update_seen` 이 **0.3m 부터** 커버리지를 칠하고 있었다. 카메라가 못 보는
거리다. 로봇이 지나가면 주변 띠가 '봤음' 으로 칠해지는데 실제로는 그 바닥을
한 번도 안 본 것이고, 거기 누운 사람이 있으면 **영원히 못 찾는다**.

`cam_see_min` 으로 뺐다. 2.0m 와 비교했지만(2머신 18런) 차이가 없어
기본값 0.3 을 유지한다. 다만 **'효과 없음' 이 아니라 '천장 효과로 측정
불가'** 다 — 포탑을 고친 뒤로 누운 조난자를 이미 거의 다 찾아서 더 올릴
여지가 없었다. 버그 자체는 실재하므로 검출이 천장에 닿지 않은 조건(더
어두운 월드, 더 작은 대상, 더 빠른 주행)에서는 다시 볼 값어치가 있다.

## 5. 유령 후보 — 세 번 시도해서 세 번 실패했다

탐사 시간의 약 30%(70분 중 17~23분)를 **유령 후보**에 쓴다. 멀리서 사람처럼
보인 대상까지 접근·정지·조준한 뒤 버리는 비용이다. 접근 전에 걸러내려 세 가지를
시도했고 **셋 다 실패했다.** 같은 길을 두 번 가지 않도록 남긴다.

**표 19. 유령 후보를 접근 전에 거르려던 세 시도**

| 시도한 신호 | 결과 |
|---|---|
| 최초 발견 **거리** | 구분 불가 — 유령 중앙 3.0 m / 진짜 3.3 m 로 겹친다. 5 m 로 자르면 유령 17건 중 4건만 감소 |
| 관측 **지속성**(1초 이상 + 좌표 산포 0.6 m) | 유령 17 → 13~18 로 런 간 편차 수준. 반면 조난자는 7/7 → 평균 6.3/7 로 손해 |
| **파인튜닝 검출기**로 프레임 단위 필터링 | 유령 11 → 14건(증가). 409번 걸러냈지만 조난자는 3/3 → 2/3 로 손해 |

셋 다 되돌렸다. 특히 세 번째에서 **왜 안 되는지**가 분명해졌다.

필터가 막는 것은 *개별 프레임의 검출*인데, 유령 판정은 *로봇이 접근해 조준했을 때
대상이 없는 것*이다. 프레임 몇 개를 막아도 후보는 다른 프레임에서 다시 뜨므로
**접근 낭비가 줄지 않는다.** 반면 진짜 조난자는 필터에 걸리면 그대로 놓친다.

즉 프레임 단위로 거르는 접근 자체가 맞지 않는다. 남은 방향은 **접근 비용을 줄이는
쪽**이다 — 조준 후 대상이 없으면 더 빨리 포기하거나, 접근 경로 중간에 재확인해
헛걸음을 조기에 끊는 것이다.

데이터 수집·학습 도구(`tools/collect_dataset.sh`, `tools/train_yolo.py`)는 남겨뒀다.
시뮬 정답으로 라벨이 자동으로 붙으므로(630장 수집, mAP50 0.738) 다른 인식 실험에
그대로 쓸 수 있다.

| `reach_check.py` | 못 찾은 런에서 거기까지 갔는지 (커버리지 문제 vs 인식 문제) |
| `inspect_near.py` | 후보로 잡기는 했는지 (관문 문제 vs YOLO 가 못 봄) |
| `det_dist.py` | 자세별 검출 거리 분포 |
| `full_find.sh` | 7/7 달성 여부와 시각 |

### 7.2 실험 설계에서 지킨 것

여러 번 잘못된 결론을 내고 정착한 규칙들이다. `tools/bench/README.md` 에
적었다.

- **조건을 번갈아 돌린다** — 몰아서 돌리면 중간에 머신이 죽었을 때 뒤쪽
  조건만 표본이 통째로 사라진다
- **라운드마다 순서를 돌린다** — 고정이면 아침에 끊길 때 늘 마지막 조건만
  표본이 적다
- **조건은 파라미터로만 가른다** — 조건마다 다시 빌드하면 빌드 차이가 섞인다
- **런 전에 노드까지 죽인다** — 고아가 쌓이면 조용히 데이터가 망가진다
- **표본이 차기 전에 판정하지 않는다** — 3~7개에서 보이던 방향이 두 배
  쌓으면 사라지는 일을 여러 번 겪었다
- **머신을 두 대 이상에서 확인한다** — 한 머신에서만 좋은 것은 두 번 다
  노이즈였다
