> **이 브랜치는 로봇 2대 구성 스냅샷이다.** 1·2·3대를 모두 포함한 최신 상태와 전체 문서는

## 초록

한 대로 재난 건물을 훑으면 큰 맵에서 시간이 모자란다. 두 번째 로봇을 붙여 구역을 갈라
맡기고, 자기 구역을 끝내면 동료를 도우러 가게 했다. 지도·표적·화재를 공유하고 목표를
선점해 같은 곳으로 몰리지 않게 한다.

56 × 40 m 재난 건물(조난자 7명 · 화재 4건)에서 **유효 런 100회 이상**으로 측정했다.

#### 주요 결과

1. **30분 제한에서 조난자 7명 전원 발견 82 % · 90 %** — 유효 50런짜리 독립 검증 2회
   ([5.2](#52-완주-성능))
2. **1대 → 2대는 약 1.4배** — 1200초 시점 발견 인원 평균 4.5 → 6.5명, 4쌍 전부 2대 승
   ([5.2](#52-완주-성능))
3. **완주율을 정하는 것은 알고리즘이 아니라 시간 예산이다** — 같은 코드로 20분 56 % →
   35분 91 % ([5.3](#53-제한-시간의-영향))

## 1. 두 번째 로봇이 하는 일

### 1.1 구역 분할

탐사 경계(`UGV_BOUNDS`)를 대수로 나눠 각 로봇에 구역을 배정한다. 스폰 좌표도 같은 규칙으로
계산해 각자 자기 구역에서 출발하게 한다.

### 1.2 동료 돕기

자기 구역의 미관측 영역이 마르면 동료 구역으로 넘어가 남은 곳을 훑는다. 한 대가 어려운
구역에 묶여도 전체 수색이 멈추지 않는다.

### 1.3 공유와 선점

지도(`map_merge`) · 표적 · 화재를 공유한다. 목표는 선점 방식이라 두 대가 같은 미관측
구역으로 몰리지 않는다.

## 2. 실행

설치·의존성은 **[SETUP.md](SETUP.md)**, 실행 상세는 **[HOW_TO_RUN.md](HOW_TO_RUN.md)** 를
따른다.

```bash
source ~/ugv_ws/install/setup.bash
export GZ_SIM_RESOURCE_PATH=~/ugv_ws/install/ugv_description/share:$GZ_SIM_RESOURCE_PATH

# 로봇 2대 병렬 수색 — 큰 월드, 실종자 7명
UGV_N_ROBOTS=2 UGV_BOUNDS=-27,-19,27,19 \
  ros2 launch ugv_bringup multi_robot_sim.launch.py \
    world:=rescue_building_large expected_victims:=7

# 한 대 기준선
ros2 launch ugv_bringup patrol_sim.launch.py \
    world:=rescue_building_large expected_victims:=7
```

## 3. 방법

### 3.1 시각 커버리지와 전장의 안개

SLAM 점유격자와 **별개의 "본 곳" 격자**를 유지한다. 라이다가 지나간 것과 카메라가 들여다본
것은 다르다. RViz 에 안개처럼 표시되며(검정=미방문 · 회색=지나갔지만 미확인 · 투명=확인
완료), 방을 통과만 하고 구석을 안 본 경우를 드러낸다.

### 3.2 정지·조준 확인 등록 (INSPECT)

이동 중 마킹하면 좌표가 튄다. 후보를 보면 **대상 앞 3.0 m 까지 접근 → 정지 → 포탑 조준 →
표본 5개 중앙값**으로 등록한다.

dedup 반경은 **관측 거리에 비례**한다. 위치 오차가 거리에 비례하므로(2.2 m 관측 → 오차
0.22 m / 4.8 m 관측 → 1.5 m) 고정 반경으로는 같은 사람을 둘로 등록한다. **중복 등록은
`expected_victims` 종료 조건을 무력화하므로** 이 부분이 중요하다.

### 3.3 자세 기반 트리아지

**다리 비율은 가림에 취약하다** — 휠체어는 바퀴가 다리를 가려 YOLO 가 기립 골격을 지어낸다.
그래서 가림에 강한 **어깨의 실제 높이**를 쓴다(깊이 + 화소 위치 + 카메라 높이, 핀홀 모델).

등급은 `L1:Critical`(누움) · `L2:NeedHelp`(부축 필요) · `L3:Normal`(자력 대피) 이다.
L2 는 '의학적으로 급함' 이 아니라 **'스스로 대피할 수 없음'** 을 뜻한다.

### 3.4 열화상 화재 감지·회피

열화상 blob 의 **모든 픽셀**로 거리를 추정한다(가장자리만 쓰면 벽으로 튄다).
`/fire_cloud` 를 Nav2 global costmap 마킹 소스로 물려 **경로 자체가 화재를 피한다.**

노드·알고리즘·토픽 전체 설계는 **[ARCHITECTURE.md](ARCHITECTURE.md)** 를 참조한다.

## 4. 실험 설계

**표 1.** 맵

| 맵 | 크기 | 조난자 | 화재 |
|---|---|---:|---:|
| `rescue_building` | 28 × 20 m | 3 | 2 |
| `rescue_building_large` | 56 × 40 m | 7 | 4 |

큰 월드의 조난자 배치는 **누움 3 / 서있음 3(잔해에 가린 1 포함) / 휠체어 1** 이며,
트리아지로는 L1 3명 · L2 1명 · L3 3명이다.

**표 2.** 실험 머신

| 머신 | CPU | RAM | GPU |
|---|---|---:|---|
| 메인 | Ryzen 7 5800X (8C/16T) | 64 GB | RTX 3060 12 GB |
| OMEN | Ryzen 9 7950X3D (16C/32T) | 32 GB | RTX 3090 Ti 24 GB |

둘 다 Ubuntu 22.04 · ROS 2 Humble · Gazebo Harmonic, `headless:=true` 오프스크린 렌더다.

### 측정 원칙

1. **유효 런만 센다.** 로봇 중 하나라도 YOLO 가 아무것도 못 본 런(키포인트 0)은 표본에서
   제외한다(`tools/gate_reject.sh`).
2. **조건을 머신에 붙이지 않는다.** 한 머신 안에서 번갈아 돌리고, 결론은 **두 머신에서
   재현될 때만** 채택한다.
3. **지표는 '고정 시점에 센 인원수'** 다(`tools/victims_at.py`). '전원 발견까지 걸린 시간'
   은 가장 늦게 찾은 한 명이 값을 정하는 최댓값 통계라 편차가 크고, 시간 안에 못 끝낸 런이
   표본에서 빠져 완주한 런만 비교하게 된다.

## 5. 결과

### 5.1 탐지·측위 정확도

**표 3.** 자동 채점(`tools/run_eval.sh`) 결과 — 큰 월드

| 항목 | 결과 |
|---|---|
| 트리아지 정확도 | **7/7** (L1 2명 · L2 1명 · L3 4명) |
| 평균 위치 오차 | **0.54 m** (표본 산포 0.01 m 이하) |
| 화재 발견 | **4/4** (오차 0.41~0.60 m) |
| 오탐 · 중복 등록 | 0건 |
| Nav2 사망 · goal 오인 | 0회 |

작은 월드도 조난자 3/3 · 트리아지 3/3 · 화재 2/2 로 합격한다.

> **주.** 표 3 은 **조난자 배치를 바꾸기 전** 값이다. 위치 오차와 화재 측위는 배치와 무관한
> 인식 스택 지표라 그대로 유효하지만 트리아지 내역은 옛 구성 기준이며, 5.2 이후 완주율은
> 모두 **바뀐 배치**에서 다시 잰 값이다.

### 5.2 완주 성능

**로봇 2대는 같은 30분에서 1대를 크게 앞선다.**

**표 4.** 큰 월드(56 × 40 m, 조난자 7명) 완주 성능

| | 1대 | 2대 |
|---|---|---|
| 7/7 완주까지 | 중앙값 **26분** (22~38분) | 중앙값 **18분** (12~30분) |
| 30분 안에 완주 | **4/7 (57 %)** | **82 % · 90 %** |
| 조난자별 발견률 | 7명 전원 7/7 | `lying_s2` 84~94 % · 나머지 96~100 % |
| 유령 검출 | 1건 / 7런 | 2건 · 1건 / 각 50런 |

2대는 **유효 50런짜리 검증을 두 번**(머신당 25런씩) 돌려 82 % 와 90 % 가 나왔다. 신뢰구간이
겹쳐 서로 모순되지 않지만, 두 검증 사이에 계측 로깅이 추가돼 코드가 완전히 같지는 않으므로
**합치지 않고 따로 적는다.** 한 번만 쟀으면 어느 쪽이든 과신이었을 폭이다.

**표 5.** 같은 머신·같은 시간대 짝지어 비교 (1200초 시점 발견 인원)

| 머신 | 2대 | 1대 |
|---|---:|---:|
| OMEN r1 | 7명 | 3명 |
| OMEN r2 | 6명 | 5명 |
| OMEN r3 | 6명 | 4명 |
| 메인 | 7명 | 6명 |

4쌍 전부 2대가 이겼고 평균 +2.0명(4.5 → 6.5)이다. 두 머신에서 재현됐다.

작은 월드(28 × 20 m)에서는 이득이 없었다. **2대가 값어치를 하려면 방이 충분히 많아야 한다.**

**표 6.** 개선 경과 (7/7 완주율)

| 설정 | 완주율 |
|---|---|
| 포탑 수평 · `seen_min_dirs` 끔 | 22 % |
| 포탑 0.20 rad | 67 % |
| **포탑 0.10 rad + `seen_min_dirs`** | **82 % · 90 %** |

원인 규명 과정은 **[docs/PR_multi_robot.md](docs/PR_multi_robot.md)** 에 있다. 요약하면
누운 조난자를 못 찾던 진짜 원인은 인식기가 아니라 **카메라 기하**였다 — 카메라 높이 0.5 m,
수직 FOV 48.9° 라 수평 조준 시 화면 아래끝이 바닥과 만나는 지점이 1.10 m 였고, 그보다 가까운
바닥은 아예 찍히지 않았다. 탐색 중 포탑을 0.10 rad 내려 해결했다.

### 5.3 제한 시간의 영향

**완주율을 정하는 것은 탐사 알고리즘이 아니라 시간 예산이다.**

못 찾은 런은 대부분 같은 조난자(남서 방 바닥에 누운 사람)를 놓친다. 그 방은 남쪽 다섯 방 중
유일하게 내부 칸막이가 있어 문이 15 m 깊이 주머니의 구석에 붙어 있다. **그 주머니 안쪽까지
내려간 런은 34런 중 33런이 찾았고, 못 내려간 런은 6런 중 0런이 찾았다.**

탐사 알고리즘의 결함으로 보고 여덟 가지를 시험했지만 이득이 확인된 것은 하나도 없었다.
제한을 45분으로 늘리자 **기본 설정이 그 조난자를 11런 전부 찾았다.** 로봇은 그 구석에 갈 줄
안다 — 30분 안에 못 갈 뿐이다.

**표 7.** 제한 시간별 7/7 완주율 (2대)

| 제한 시간 | 완주율 |
|---|---|
| 20분 | 56 % |
| 25분 | 77 % |
| **30분** | **86 %** |
| 35분 | 91 % |
| 40분 이상 | 91 % |

86 % 는 알고리즘의 한계가 아니라 30분이라는 예산의 값이다. 더 올리려면 탐사 정책이 아니라
시간이나 로봇 대수를 늘리는 쪽이다.

> 로봇을 3대로 늘리면 어떻게 되는지는 [`main`](../../tree/main) 의 대수 확장 실험에 있다.
> 결론만 적으면 **3대는 이득이 없다.**

## 6. 한계와 남은 과제

1. **탐사 시간의 약 30 %(70분 중 17~23분)를 유령 후보에 쓴다.** 멀리서 사람처럼 보인 대상까지
   접근·정지·조준한 뒤 버리는 비용이다. 접근 전에 걸러내려 세 가지를 시도했고 **셋 다
   실패했다** — 프레임 단위 필터링으로는 접근 낭비가 줄지 않는다(후보가 다른 프레임에서 다시
   뜨므로). 남은 방향은 접근 비용 자체를 줄이는 쪽이다.
2. **오탐이 인원수를 채우면 '전원 발견' 이 잘못 보고된다.** 실제로 1회 발생했다(잔해와 벽
   사이 빈 공간을 사람으로 인식). 채점기는 이 사고를 자동으로 잡는다.
3. 커버리지 완주 후의 회차 완료 보고는 아직 실측하지 못했다.
4. 직선 접근이 막혔을 때의 우회 접근은 단위 테스트로만 검증됐다(실측 발동 0회).
5. 실로봇 통합은 진행 중이다. 열화상 카메라는 시뮬 전용이다.
